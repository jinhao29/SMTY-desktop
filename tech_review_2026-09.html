总体结论

两端工程质量在同类个人/小团队项目中属中上水平：模块边界在构建层干净、无危险反序列化、无 SQL 注入、Zip 穿越防护到位、更新链 sha256 fail-closed、跨线程 UI 操作全部合规。这些是很多项目做不到的。

但存在 3 个 P0，且高度集中在一个主题上——未成年人敏感个人信息的明文落地。Room 数据库未加密（20 张实体表含姓名/电话/身高体重）、备份 ZIP 未加密、桌面端主数据 .xlsx 非原子写。前两项是合规与泄露风险，第三项是实打实的数据丢失风险：一个 wb.save() 中途断电，整个学员档案就废了。

架构上真正的债不在"分层不清"，而在 God 类：Android 端 31 个超 500 行文件（最大 PreClassTab.kt 1485 行），桌面端 ui_template_screen.py 里 SingleTab 一个类扛 500 行。测试则是两端共同短板——核心数据层与加解密模块零覆盖。

04整体风险评估

风险场景概率影响说明与关联项
主数据文件损坏 中高 灾难级 8 处非原子写 + 锁删除反模式 + 读未加锁，三者叠加。写入中断一次即可能丢失整个档案目录。这是当前最大的单点风险，但也是最容易修的（约 30 行）。关联 DES-01 / DES-02 / DES-03。
学员信息明文泄露 中 严重 Room 明文 + 备份 ZIP 明文 + allowBackup + 密钥种子明文，形成一条完整泄露链。设备丢失或备份外发即触发。涉及未成年人个人信息，有合规责任。关联 AND-01/02/03/04。
伪造心跳劫持照片上传 低 严重 需要攻击者与目标同处一个局域网（培训机构公共 WiFi 是现实场景）。一旦发生，学员照片直接外泄到攻击者主机。关联 AND-06。
静默数据丢失 中 高 写路径 except 吞异常 + 全局 excepthook 无提示。用户以为保存成功，实际失败。与"文件损坏"不同，这个是悄无声息的，往往几周后才发现。关联 DES-10 / DES-11。
重构引发回归 高 中 31 个 Android God 类 + 桌面端核心数据层零测试。任何人动这些文件都是"盲改"，且没有 CI 与覆盖率门禁兜底。关联 AND-10 / AND-17 / DES-12。
供应链投毒（更新通道） 低 高 两端更新均依赖 GitHub Release，桌面端为同信道哈希、Android 端已有 UpdateIntegrity。GitHub 账号失陷是唯一前提，概率低但影响面覆盖全部用户。关联 DES-06。

风险评估的一句话总结

最紧迫的不是"被黑客攻击"，而是"自己把数据弄丢"。三个 P0 里，DES-01（xlsx 非原子写）修起来只要 30 行代码，却能消除最大的单点风险 —— 建议今天就做。Android 端的加密改造工作量大得多，但可以先做 allowBackup=false 和日志剥离这两个低成本动作，把最容易触发的泄露路径先堵上。
