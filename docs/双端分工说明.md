# 双端分工说明

> 版本：v67（2026-09-14）｜ 适用：SMTY-desktop（PC）+ SMTY（Android）+ 小程序
> 本文是双端功能差异的**判定记录**：为什么某些功能只存在于一端，哪些差异是有意为之。

## 判定标准（唯一标准）

**这项功能是否属于该端的职责范围？**

| 情形 | 判定 | 处理 |
|---|---|---|
| 属于该端、但没做 | 真缺口 | 补，且优先复用已有组件 |
| 不属于该端 | 设计差异 | 记录在案，明确**不补** |
| 有功能代码、无入口 | 死代码 | 要么接线，要么删除 |

**禁止「哪端缺就补哪端」的无脑对齐。** 两端定位不同，功能面本就不该对称。

## 一、现场端 · Android（课时发生的地方）

职责：**课上 / 课下即时录入**——所有现场动作在手机上完成，手机是数据的源头。

| 能力 | 入口 / 实现 |
|---|---|
| 排课 | `ScheduleScreen`（学员周课表）、`CoachLessonGridTab`（教练周课表）、`AutoScheduleFromPackageDialog`（按课时包一键排课/小班课/体验课）、`LongTermSchedulePlanner`（28 天窗口长期排课） |
| 签到 / 签退 | `LessonCheckInScreen`（拍照、批量、未签退筛选）。**扣课时只发生在签退**（单一扣费点） |
| 课后反馈 | `PostClassTab`（训练态度 / 表现 1-10 / 下次课目标 / 教练寄语，存 `lessons` 表列） |
| 现场收款 | 课时包卡片「收款」：写收费流水 + 累加包实收（`FeeRecord.stableKey` 自然键幂等） |
| 体测成绩录入 | `ScoringScreen` + `core/Scorer`（现场录、实时算分） |
| 成长报告（发家长） | `GrowthScreen` + `GrowthPdfGenerator`（加密 PDF + 4 位密码 + 微信直发） |
| 教练管理 | `CoachManageScreen` 5 Tab：档案 / 排课 / 工作量 / 团队 / **薪资（结算 + 提现 + 审核 + 报表）** |
| 学员建档 | `AddStudentScreen`（含智能粘贴批量导入）；遗传数据（父/母身高）在**身高预测页**就录 |
| 数据出口 | 备份 ZIP（db + `export_meta.json` + `fees[]` + `coaches[]` + 签到照片）、双端同步、系统分享 |

## 二、整理端 · PC（课后整理与汇总的地方）

职责：**批量 Excel、备份恢复、学员详情总览、桌面级报告**。

| 能力 | 入口 / 实现 |
|---|---|
| 学员建档（含 5 个遗传/生活方式字段） | 父身高 / 母身高 / 睡眠 / 营养评分 / 周运动 —— Android 建档表单**没有**这些，见「不补清单」 |
| 体测成绩批量录入 + 自动评分 | 体测页表格 → `standards.py` / `scorer.py` |
| 上课记录 / 课后反馈补录 | 「记录一次上课」→ `LessonWindow`；「填写课后反馈」→ `LessonFeedbackDialog`（批 1 接线） |
| 收费录入与对账 | `fee_manager` 是**收费口径真源**；时间段筛选、导出欠费清单（批 2/3） |
| 教练管理 | **只读镜像**（v67 D2）：数据来自手机备份 `coaches[]`，PC 不提供新增/编辑 |
| 备份恢复 + 时光机快照 | 数据中心「数据备份与导入」「时光机」 |
| 双端同步服务 | UDP 心跳 + USB `adb reverse` + 配对码签名（随主程序自动启动） |
| 续费预警 / 成长报告 PDF / 训练计划下发 | 数据中心 + 训练工具 |
| Excel 导入导出 / 自动更新 | 备份页导入模板、学员汇总导出、GitHub Release 更新 |

## 三、不补清单（逐条写理由）

| 事项 | 现状 | 不补的理由 |
|---|---|---|
| PC 排课编辑 | PC 只有只读达成率分析器（`schedule_lesson_analyzer`） | 排课是现场动作，手机上按教练/学员两个视角排最顺；PC 侧保留分析器做**事后复盘**已够 |
| PC 签到 / 签退 | 无 | 现场动作，PC 代签没有业务意义（D 拍板：不做 PC 端签到签退） |
| PC 教练薪资结算 | 无（v67 起 PC 教练页转只读镜像） | 结算依赖消课数、提现、团队层级，全在手机；PC 只有 6 个基础字段，补齐等于把整套薪资模型复制一遍 |
| Android 建档表单缺 5 个遗传字段 | 实体有列，入口在身高预测页 | **不是缺口**：父/母身高在「要预测时才录」最自然（就录即算、自动回写档案）；塞进建档表单会加重每次建档的填表负担 |
| Android 粘贴导入字段与建档表单不同源 | 粘贴格式：姓名/小区/课程内容/代课教练/课时包 | 有意设计：粘贴源是微信接单文案的自然格式，不是表单字段的镜像 |
| PC 无学员周课表视图 | 无 | 现场看课表在手机；PC 的「训练达成率分析」已覆盖整理需求 |
| Android 无 Excel 批量导入导出 | 无 | 批量整理是桌面活；手机侧走「粘贴批量导入」轻量路径已够 |
| 小程序与双端零交换 | 无 | 协议级改动，收益低（本轮明确不做） |

## 四、双源风险备案（**改一处必须改两处**）

1. **体测标准双份硬编码**
   PC `standards.py` ↔ Android `core/Standards.kt`（小学国标 / 深圳中考 2026 新方案 / 2025 旧方案）。
   改标准**必须双端同改**：PC 侧由 `test_standards_parity.py`（75 例，含锚定 Android 五个规则常量）把关，
   Android 侧有 `ScorerFullwidthTest`。顺序建议：先改 PC（测试更全），再对照 Android 常量。

2. **成绩解析规则**
   全角标点归一化必须双端同改：PC `scorer.normalize_input` ↔ Android `Scorer.normalizeInput`；
   且**归一化必须在负数拦截之前**（`分:秒` 语义）。

3. **课后反馈两端各存**（D3 拍板：只做字段映射、不统一字段）
   PC 存 `课堂反馈.xlsx`，Android 存 `lessons` 表列，互不相通。字段映射见
   `docs/reports/feedback_field_mapping.md`。**不新增同步**是拍板结论，不是遗漏。

4. **扣课时时机**
   Android 签退扣（单一扣费点）；小程序历史上签到即扣 —— 已知漂移，勿在未对齐前改动任一端。

5. **教练字段导出面**
   Android 备份只导出 coaches 的 4 个字段（`name` / `phone` / `specialty` / `status`），
   PC 只读镜像就展示这 4 列（角色 / 入职日期 / 备注留空）。
   若日后要在 PC 展示更多字段，**必须先在 Android `BackupManager` 扩导出**（协议改动），
   再改 PC UI —— 不允许用"PC 侧猜"的方式补字段。

6. **收费口径**
   `fee_manager` 为真源：单价 = 实收 ÷ 已购课时；应收 = 总课时 × 单价；待收 = 应收 − 实收。
   **应收 / 待收恒为全量口径**（由课时包决定），只有实收随时间区间变化。

## 六、数据互通现状（协议 v23）

**已通**：备份 / 加密互通、UDP 心跳与设备信任、手机 → PC 合并（`students` / `lessons` / `packages` / `fees[]` / `coaches[]`）、PC → 手机下发。

协议细节见 `android_app/desktop_sync/双端同步协议.md`。
